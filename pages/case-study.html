Development Case Study

Making a Learning Experiment Playable

How I turned a maze-navigation learning project into a browser experience visitors can actually use—and the choices I made to keep it reliable, approachable, and technically honest.

By Alysha Pursley

Project brief: make the work understandable

Treasure Hunt started as a Python/Jupyter experiment in maze navigation through deep Q-learning. Its code demonstrates an environment, rewards, action selection, replay memory, and a training workflow. That was useful source to study, but a notebook alone wasn't the experience I wanted someone to encounter when opening my portfolio.

The problem I chose to solve next was a presentation and product problem: how could I let visitors experience the challenge immediately, while still making the original learning project easy to inspect? I decided to build a separate browser game rather than pretend the notebook's neural network was running online.

The goals I designed around

I set four practical goals. First, visitors should be able to start a maze race without installing Python or creating an account. Second, generated rounds should have a reachable treasure. Third, controls and race status should make sense whether someone uses a keyboard or on-screen buttons. Finally, the project should be honest and easy to navigate for someone interested in the engineering.

These goals shaped the architecture more than any desire to add a framework or an online service. The game runs as static HTML, CSS, and JavaScript, and the original learning sources remain available as a separate part of the repository.

Turning a concept into a reliable game

I separated the browser implementation into three responsibilities: the maze module owns the board and legal movement, the competitive agent chooses moves, and the app coordinates the interface and race lifecycle. This means a change to the presentation doesn't have to redefine which movements are valid.

The maze generator builds possible routes and checks that the target can be reached; it retains a fallback board when generation attempts do not produce a suitable maze. The computer opponent uses pathfinding with difficulty-dependent pacing and exploration. I deliberately kept that approach separate from the learning algorithm in the Python notebook.

Designing for an actual visitor

I used a dark visual palette with high-contrast lime accents, visible race controls, and recognizable player, opponent, wall, and goal states. The game supports arrow keys, WASD, and on-screen directional buttons. Supporting pages explain the project to visitors who want more than the game itself.

Mobile layouts require more than reducing font size. The site uses responsive navigation and flexible content widths, including a compact menu for narrower viewports. I also provide a dedicated 404 page and clear routes back to the playable game and project information.

Decisions and trade-offs

Static hosting makes the browser demo straightforward to open and inspect. It also means the website does not execute Python training, save personal game accounts, or serve a trained model. That's a deliberate boundary rather than a feature I hide.

Likewise, using a computed route for the browser opponent is a practical design choice: it can deliver predictable movement for an interactive race, while the notebook remains the place to examine how an agent might learn from rewards. The dedicated articles explain those algorithms in depth; this case study focuses on why I made the product and engineering decisions.

What I could verify—and what remains

The project has passed automated checks for browser maze behavior, opponent input validation, Python environment behavior, and static-page references. These tests help catch regressions in the code, but they are not proof of a flawless experience on every browser or assistive device.

A reproducible modern TensorFlow training run has not been established for the original notebook. Live mobile and screen-reader evaluations are separate follow-up work. I want the portfolio to show the implementation and its limits accurately rather than imply evidence I do not have.

The result and what I learned

The result is a standalone maze race that visitors can play, supported by the original Python learning project, four focused technical articles, and clear paths through the source. The browser experience has its own decision engine; it doesn't impersonate a trained neural network.

The most valuable lesson was to design for both the person using the project and the person reviewing its code. Clear responsibilities, explicit limits, and an honest explanation of trade-offs make the work stronger than adding technology merely to make the list of tools longer.
