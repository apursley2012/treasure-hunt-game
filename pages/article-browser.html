Browser Engineering

From Notebook to Browser — Building a Playable Maze Race

How a solvable maze generator, pathfinding opponent, and responsive controls turn a learning concept into an interactive browser game.

By Alysha Pursley

A portfolio project needs a way to be experienced, not just described. The browser edition of Treasure Hunt turns the same maze-navigation challenge into a race between a human player and a computer-controlled opponent. It keeps the rules recognizable while making the experience available through a static website.

This is a separate JavaScript implementation. Its opponent uses pathfinding, not the trained Python neural network. That difference is intentional: the browser version prioritizes immediate interaction, straightforward deployment, and transparent behavior.

The first requirement: every round must be playable

Randomly generated walls create variety, but they also introduce a failure mode: the treasure might become unreachable. The maze generator checks for a valid route before accepting a board and can fall back to a known configuration. That invariant matters more than simply producing a visually different grid.

Movement rules are shared by the player and the opponent. The maze logic decides whether a move stays in bounds and avoids blocked cells, so the interface cannot quietly invent a different set of rules.

The generator is not just scattering walls at random. It builds a connected corridor, adds dead ends, and checks the resulting route. Generation attempts are bounded, and a solvable fallback prevents an unusable round. This is a practical trade-off: variety is valuable only if the game remains winnable.

An opponent that can be understood

The computer-controlled racer uses shortest-path information to move toward the treasure. On more challenging settings, it follows that information more directly. Easier settings introduce different pacing and occasional less direct choices, giving visitors a meaningful way to adjust the race.

These settings are game-design parameters, not machine-learning training controls. Being precise about that distinction helps visitors evaluate the browser engineering on its own merits.

The opponent recomputes a shortest route after moving, which matters when an exploratory choice takes it away from the earlier path. Hard mode removes hesitation and exploratory probability; easier modes use both, along with slower movement and longer start delays. Those values shape a race rather than train a neural network.

Separating game rules from interface code

The maze module handles board state, movement constraints, route utilities, and solvable generation. The opponent module handles decisions and difficulty behavior. The application module connects those pieces to rendering, keyboard and on-screen controls, race timing, and round feedback.

That separation has a practical benefit: a movement rule can be tested without clicking through the page, and a visual change does not need to alter the pathfinding algorithm. The structure is deliberately modest because the project does not need a larger application framework.

The game state is distributed deliberately. TreasureMaze owns the player and environment; CompetitiveAgent owns the opponent's position and trail; app.js owns the race lifecycle, controls, timers, and rendering. Resetting a race clears active timers and reconstructs the relevant state together, avoiding an opponent continuing to move after a new round begins.

Designing for visitors, not only developers

The game gives visitors a direct way to discover the problem: choose a route, observe the opponent, and try another round. The supporting pages then provide the technical context for those who want it. This progression makes the project accessible to both casual visitors and people evaluating its implementation.

Responsive controls, consistent site navigation, and clear page links matter because the project is meant to be explored outside a development environment. A static site also avoids a sign-in requirement or server-side state.

The dark visual system uses bright accents to distinguish the game board and actions. On-screen controls, keyboard arrows, and WASD offer multiple ways to play; the keyboard handler avoids intercepting shortcuts while the user is interacting with native controls. Grid-cell labels communicate position and state to accessibility APIs. These are implementation choices, not proof of a completed assistive-technology audit.

How the browser version is verified

JavaScript tests exercise movement constraints, route reachability, randomized board invariants, and opponent configuration. Source checks cover syntax and local asset references. Those checks protect important behavior while leaving room for real-browser accessibility and visual testing.

The most useful outcome is a demonstration whose behavior can be explained from its source. The race does not need to pretend to be a deployed neural network to show thoughtful application design.

Tests can verify movement constraints, generated-board reachability, opponent settings, and reset flows without loading the entire website. A simulated DOM can also exercise application controls, but it cannot replace real-browser checks of layout, focus, touch behavior, or screen-reader announcements.
